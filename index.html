The move

Regist3r R3apers open with the oldest trick in the book, aimed carefully. Utility staff receive a plausible IT notice — your single sign-on password is expiring — linking to a pixel-perfect copy of the organization's Keycloak login page.

One employee types in real credentials. That single password is the key to the whole identity side of the operation — everything the crew learns about the plant starts here.

How it unfolds

  1. Open-source recon identifies the real SSO portal's branding, naming, and login flow.
  2. A lookalike domain hosts a cloned login page that mirrors the genuine Keycloak theme.
  3. The lure goes to staff mailboxes; submitted credentials are captured in real time.

What defenders can see

  • The lure arriving in the inbound mail logs at the gateway
  • The user clicking the link, visible in proxy and click telemetry
  • Authentication events in the Keycloak logs as the harvested credential is replayed against the real identity provider

Defender lesson

Phishing-resistant MFA — passkeys or FIDO2 keys — breaks this chain at step one. A password alone is a single point of failure for the whole plant.

The move

The password's real value shows here. Signed in as a legitimate user, the crew walks the organization's source control — its GitHub-style repositories on Gitea — the way an insider would: organization by organization, repository by repository, cataloguing projects, permissions, and history.

Nothing is exploited and nothing is forced. This phase builds a map: what exists, who owns it, and which repositories describe how the plant actually runs. The interesting ones get cloned in bulk and taken away for quiet study.

How it unfolds

  1. The actor signs in with the phished credentials — the same SSO the real user uses, through Keycloak.
  2. Organizations, repositories, and the account's permissions across them are enumerated.
  3. Keyword searches — hmi, register, modbus, api, config — rank the repositories worth taking.
  4. Candidate repositories are bulk-cloned for offline analysis.

What defenders can see

  • Repository access from outside the organization — an unfamiliar network and geography for the account
  • Bulk clones or downloads far outside the account's normal working pattern
  • Wide enumeration and search by an account that never normally touches code

Defender lesson

Source control is production-adjacent. Scope repository access to need, audit who can read integration projects, and log search and clone activity like you would a database.

The move

Study pays off. Among the cloned repositories sit the plant's own legitimate workflow documents — including the register map, the engineering reference that says which HMI addresses drive pumps, valves, and chemical dosing. And in a committed configuration file, history included, is the API key the plant's tooling uses to talk to that HMI.

The map tells the crew exactly what a write will do; the key lets them ask the API politely and be answered. They validate the key with read-only calls and learn the API's shape before ever changing a value.

How it unfolds

  1. The workflow documents and register map are extracted from the cloned repositories.
  2. The HMI API key is recovered from a config file — and from its commit history.
  3. The key is tested with read-only API calls to confirm it works and map the endpoints.
  4. A target list is built: the registers whose manipulation will be felt in the process.

What defenders can see

  • Downloads of engineering documents by accounts with no engineering role
  • Secret-scanning alerts on credentials committed to repositories
  • The API key used from an unusual host — read calls outside the normal tooling pattern

Defender lesson

Secrets never live in repositories — scan for them, rotate on any exposure, and treat register maps as sensitive engineering data with the same handling as credentials.

The move

Not every door is guarded by a password. The utility publishes a public "outage map" so customers can see which neighborhoods are without water — a GeoServer instance, internet-facing, sitting in the DMZ, and behind on patches.

The crew exploits a known vulnerability in that GeoServer service and gets code execution on the map server. They now hold a second, independent foothold — this one inside the DMZ, the segment that hosts everything public.

How it unfolds

  1. Recon of the utility's public services identifies the outage map and its GeoServer fingerprint.
  2. A known, unpatched GeoServer vulnerability is exploited for remote code execution.
  3. A foothold is established on the map server inside the DMZ.
  4. The crew orients: what this host is, what it can reach, and what reaches it.

What defenders can see

  • Exploit-shaped requests and error spikes in the GeoServer and web server logs
  • The GeoServer service spawning shells or unexpected child processes
  • New outbound or internal connections from a host that normally only serves map tiles

Defender lesson

Public-facing services are part of the plant's attack surface. Patch them like it, watch them like it — and assume anything living in the DMZ may already be hostile.

What this phase needs on the range

The move

The map service runs in Docker, and the container can reach the host's Docker socket — root, waiting to be asked. The crew starts a new container with root-level privileges over the host, mounts the host filesystem, and owns the DMZ box outright.

From that height they enumerate the DMZ's routes and find the OT "bridge": the endpoint where the HMI lives. The bridge is the plant's blocker — it forwards nothing directly to the PLC. The only permitted path through it is port 1881, to the HMI and its API.

How it unfolds

  1. The accessible Docker socket is discovered from inside the compromised service.
  2. A privileged container is created, mounting the host — a clean escape to host root.
  3. The DMZ is enumerated from the host: routes, neighbors, and reachable services.
  4. The OT bridge is identified; probing confirms port 1881 to the HMI/API is open — and direct access to the PLC is refused.

What defenders can see

  • Container-creation events and Docker socket access on a production host
  • A new privileged container that matches no deployment baseline
  • Enumeration and scanning traffic sourced from inside the DMZ
  • Denied connection attempts from the DMZ toward PLC addresses

Defender lesson

The Docker socket is root by another name — no workload should ever reach it. And segmentation only counts when the one allowed path is narrow, logged, and watched.

What this phase needs on the range

DMZ Docker host with a reachable socket · OT bridge endpoint · HMI/API on port 1881 · PLC reachable only through the bridge rules

The move

Everything converges. From the compromised host in the DMZ, the actor reaches through the bridge on port 1881 and calls the HMI API — authenticating with the stolen key and writing registers chosen straight from the stolen map: pumps commanded, setpoints shifted, chemical dosing altered.

No malware touches a controller, and no request is malformed. Each call is authorized on paper; only the intent is hostile — and the simulated treatment process responds exactly as the real one would.

How it unfolds

  1. API calls are issued from the DMZ foothold, through the OT bridge on port 1881.
  2. Writes target the registers selected back in Phase 3 for maximum visible effect.
  3. Operators watch process values drift on the HMI with no local action to explain them.

What defenders can see

  • HMI and API logs showing write activity sourced from the DMZ
  • Setpoint changes with no matching operator action
  • Process values trending outside their normal envelope

Defender lesson

Authenticate and authorize every API write, alarm on out-of-envelope values, and require human confirmation for critical setpoints. A valid key should never be the whole story.

The players & the range

Threat actor

Regist3r R3apers

A fictional hacktivist crew — the name is the tell: their endgame is the register map of a water plant, and they get there through other people's trust: stolen passwords, their own documents, and public services nobody patched.

  • Motivation
    Publicity and embarrassment — prove a water utility can be reached, then claim credit
  • Tradecraft
    Identity-first: phishing, valid accounts, trusted tooling, legitimate APIs
  • Objective
    Manipulate the simulated treatment process via the HMI API
  • Notably absent
    No zero-days, no brute force, no malware on controllers
