The move

Regist3r R3apers open with the oldest trick in the book, aimed carefully. Utility staff receive a plausible IT notice — your single sign-on password is expiring — linking to a pixel-perfect copy of the organization's Keycloak login page.

One employee types in real credentials. That single password is the only exploit the crew needs for the entire operation.

How it unfolds

  1. Open-source recon identifies the real SSO portal's branding, naming, and login flow.
  2. A lookalike domain hosts a cloned login page that mirrors the genuine Keycloak theme.
  3. The lure goes to staff mailboxes; submitted credentials are captured in real time.

What defenders can see

  • A newly registered lookalike domain in mail gateway logs
  • User reports through the phish button
  • A successful login from an unfamiliar source shortly after

Defender lesson

Phishing-resistant MFA — passkeys or FIDO2 keys — breaks this chain at step one. A password alone is a single point of failure for the whole plant.

What this phase needs on the range

The move

No exploit, no escalation — the crew simply logs in. Keycloak is the front door to every application federated behind it, so one working identity quietly unlocks mail, internal apps, and source control.

The session token the IdP issues is now the actor's passport, indistinguishable from the real user's own sign-in.

How it unfolds

  1. The actor authenticates to the real Keycloak realm with the harvested credentials.
  2. The issued SSO session is used to enumerate which applications the account can reach.
  3. Source control — Gitea — stands out: same login, far richer target.

What defenders can see

  • IdP login from a new network, geography, or device fingerprint
  • Off-hours authentication against the account's normal pattern
  • Session tokens presented from two places at once

Defender lesson

Treat the identity provider as a tier-0 asset: alert on anomalous logins, enforce conditional access, and make session revocation a one-click response — it cuts the actor's passport off mid-chain.

What this phase needs on the range

Keycloak realm · SSO federation to Gitea and internal apps

The move

With a legitimate seat inside Gitea, the crew searches the way any curious insider would: hmi, register, modbus, api. One repository documents exactly how the vendor tooling talks to the plant's human-machine interface.

Source control stops being a developer convenience and becomes an intelligence archive on how the process is wired.

How it unfolds

  1. Organizations, projects, and permissions visible to the account are enumerated.
  2. Keyword search surfaces the HMI integration repository and its documentation.
  3. READMEs, commit history, and config examples reveal the integration's design.

What defenders can see

  • Repository enumeration and search by an account that never touches code
  • Bulk clones or downloads outside normal working patterns
  • Access reviews showing standing access far beyond job need

Defender lesson

Source control is production-adjacent. Scope repository access to need, audit who can read integration projects, and log search and clone activity like you would a database.

Techniques

T1213 Data from Information Repositories T1083 File and Directory Discovery

What this phase needs on the range

Seeded Gitea organization · HMI integration repository with realistic docs

The move

Buried in the repository are the two artifacts that turn access into capability: the API key the vendor tooling uses to talk to the HMI, and the register map — the engineering document that says which addresses drive pumps, valves, and chemical dosing.

With the map, the actor doesn't have to guess what a write will do. They can read the process like a manual.

How it unfolds

  1. The API key is recovered from a committed configuration file and its history.
  2. The register map is extracted from project documentation and spreadsheets.
  3. A short target list is built: the registers whose manipulation will be felt.

What defenders can see

  • Secret-scanning alerts on committed credentials
  • Downloads of engineering documents by non-engineering accounts
  • An API key that has never been rotated suddenly mattering

Defender lesson

Secrets never live in repositories — scan for them, rotate on any exposure, and treat register maps as sensitive engineering data with the same handling as credentials.

T1552.001 Credentials in Files T1005 Data from Local System

What this phase needs on the range

Planted API key in repo config · register map documentation

The move

The crew doesn't attack the plant — they attack what the plant trusts. A vendor diagnostic utility, the kind technicians run without a second thought, is quietly modified so its next routine update carries the actor's code along with it.

The version bump looks mundane. The signature check that would catch it was never enforced.

How it unfolds

  1. The utility's source or distribution package is altered using the access already gained.
  2. The change is dressed as a routine maintenance release.
  3. It is published through the normal channel the technicians already trust.

What defenders can see

  • Binaries whose hashes don't match the vendor's published values
  • Missing or invalid code signatures on an OT-adjacent tool
  • An update appearing outside the vendor's normal release pattern

Defender lesson

Verify what you run. Code signing, hash verification, and a controlled update path are non-negotiable for any software allowed to touch operational systems.

T1195.002 Compromise Software Supply Chain T1036 Masquerading

What this phase needs on the range

Vendor utility + update mechanism · an enforced-nowhere signing policy

The move

One workstation lives in both worlds: it reads IT email and reaches OT systems, because that's how a small utility gets maintenance done. When the poisoned utility runs there during routine work, the actor crosses the seam defenders assumed was a wall.

From that single foothold, the internal HMI API — never designed to face a hostile caller — is suddenly in reach.

How it unfolds

  1. A technician runs the updated utility as part of normal maintenance.
  2. The embedded code activates on the dual-hatted endpoint and establishes the actor's path inward.
  3. The actor stages from the endpoint toward the OT segment's HMI services.

What defenders can see

  • A diagnostic utility spawning shells or unexpected network connections
  • New traffic flows from the IT side toward OT addresses
  • Endpoint telemetry showing the tool behaving unlike its baseline

Defender lesson

Dual-hatted endpoints quietly dissolve segmentation. Dedicated jump hosts, application allow-listing, and tightly brokered paths across the seam are what make the boundary real.

Techniques

T1204.002 Malicious File T1021 Remote Services

What this phase needs on the range

Dual-homed workstation · segmented IT and OT networks to cross

The move

The endgame needs no malware on a controller and no exploit at all. The actor calls the plant's own HMI API, authenticates with the plant's own key, and writes register values straight from the stolen map: pumps commanded, setpoints shifted, dosing altered.

Every request is well-formed and authorized on paper. Only the intent is hostile — and the simulated process responds exactly as the real one would.

How it unfolds

  1. API calls are issued from the bridged endpoint using the recovered key.
  2. Writes target the registers chosen back in Phase 4 for maximum visible effect.
  3. Operators see process values drift on the HMI with no local action to explain them.

What defenders can see

  • API writes originating from an unusual host or account context
  • Setpoint changes with no matching operator action
  • Process values trending outside their normal envelope

Defender lesson

Authenticate and authorize every API write, alarm on out-of-envelope values, and require human confirmation for critical setpoints. A valid key should never be the whole story.
